## 9. Round-2 candidate study (shortCircuit shipped in 0.3.0; reuseMeasure still research-only)

After the 0.2.0 release, two further algorithm candidates were measured with `research/candidate-round2.mjs` (results in `research/candidate-round2-results.json`). Every variant was checked byte-for-byte against the official `pruneContent`, and `pruneSession` results plus derived messages were checked against the shipping implementation. Node v24.16.0 / darwin/arm64, 10 warmups, 60 alternating samples, P50 milliseconds.

| Case | Shipping | +shortCircuit | +reuseMeasure | +both |
|---|---:|---:|---:|---:|
| `pruneContent` within 1k | 0.0026 | 0.0003 (**90.3%**) | 0.0026 | 0.0003 |
| `pruneContent` within 8k ASCII | 0.0137 | 0.0002 (**98.5%**) | 0.0136 | 0.0002 |
| `pruneContent` within 8k emoji | 0.0118 | 0.0002 (**98.6%**) | 0.0118 | 0.0002 |
| `pruneContent` over 300k | 0.7109 | 0.7129 (-0.3%) | 0.7126 | 0.7065 |
| `pruneSession` one short result | 0.0678 | 0.0666 | 0.0700 | 0.0708 |
| `pruneSession` one large result | 1.2620 | 1.2305 | 0.7070 (**44.0%**) | 0.7137 |
| `pruneSession` 8 mixed results | 1.6417 | 1.5862 | 0.9788 (**40.4%**) | 0.9934 |

- **shortCircuit (upper-bound pruning):** the number of Unicode code points is never greater than the UTF-16 length, so if the sum of `text.length` over text blocks is at most `thresholdChars`, the content is definitely within budget and `pruneContent` can return `null` without scanning any text. Semantics are identical with no immutability assumption, and large over-budget inputs show no measurable regression (only a few extra `.length` reads). This is the more attractive candidate because most tool results are within budget.
- **reuseMeasure (session-scoped measurement reuse):** upstream `pruneSession` measures the same content array twice (once as `pruneContent`'s total, once as `charsBefore`). A `WeakMap` local to one `pruneSession` call, keyed by array identity, can return the value already computed. It helps large sessions but adds a small cost to short ones (-3.3% P50) and **depends on the content array not being mutated inside the call stack**. That precondition is a real design constraint, not a formality.
- Combining both is not additive on short sessions (-4.6% P50) and sometimes has worse P95 than `reuseMeasure` alone.

**Status in 0.2.0:** neither candidate was in the shipped `src/index.js`, in any preset, in any Web button, or in the 0.2.0 tarball.

**Status in 0.3.0:** `shortCircuit` was adopted as a third independent config switch (default `true`) in `src/index.js`, using the upper-bound check described above. It deliberately adds **no preset id and no Web button**: Web sessions inherit it through the provider default, so session-log compatibility with 0.2.0 is preserved. `reuseMeasure` remains research-only because its immutability precondition and short-session regression are unresolved. Neither candidate carries real-model evidence (§7). The research table above predates adoption; the shipped implementation is covered by the eight-state parity tests and the eight-case benchmark as they stood in 0.3.0 (§3 then described 18 tests; §3 now documents the 0.4.0 suite) and by the runtime probe (§10). P95 is noisy on this machine and 60 samples is a small sample.

**Status in 0.4.0:** `sessionMetrics` supersedes the research-only `reuseMeasure` idea with a different design. Instead of assuming content arrays are never mutated, it verifies an O(block-count) structural snapshot on every hit (array length, each block's `type`, each text block's immutable `text`) and derives `charsAfter` from code-point positions already computed during pruning. The cache is created lazily on the first over-budget result, so the short-session regression that disqualified `reuseMeasure` does not appear: the `within-budget` session is 0.0015 ms with and without the cache, with 0 exact scans in both. Over-budget session shapes are 46.2–51.6% lower P50 than the 0.3.0 path (§11). It is a config-level switch with no preset id and no Web button. `reuseMeasure` itself is still research-only and is not shipped. Neither candidate carries real-model evidence (§7).

## 11. 0.4.0 change and re-verification

**What actually changed.** A fourth independent config switch `sessionMetrics` (default `true`) in `src/index.js`, plus one new runtime file `src/metrics-cache.js`. `pruneSession` wraps one synchronous call in a lazily created, structure-verified `WeakMap`; `measureContent` consults it; `pruneContent` derives `charsAfter` from code-point positions it already computed instead of rescanning the pruned text. A hit requires the array length, every block's `type` and each text block's `text` to match a flat snapshot. Strings are immutable and non-text blocks contribute zero, so a matching snapshot proves the code-point total cannot have changed; pushing, splicing, replacing a block, flipping a type or assigning a different text invalidates the entry and falls back to an exact scan. The cache is disposed in `try/finally`; nested calls save and restore the previous state. It is created only on the first result that actually exceeds the threshold, so an all-within-budget session allocates nothing. `sessionMetrics: false` restores the 0.3.0 path exactly.

## 13. 0.4.1 change and re-verification

**What actually changed.** This is a hardening release with **no new optimization and no switch change**. It closes the three non-blocking items left by the 0.4.0 independent read-only review (`v040-quick-review`):

- *Whole-block string reuse* (keep the original string when a block is entirely in the head or tail): −6.2% to +0.2% versus the identical linear baseline across two runs, direction unstable, P95 noisier. **Not shipped** — V8 already optimizes whole-string `slice` and empty concatenation; there is no measurable gain, only extra branches.
